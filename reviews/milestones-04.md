## Findings

1. **AC3 contradicts DESIGN.md 24.3 rule 1.** The rule says dispatch copies *only the attempt record* (`build.md` or `verification.yaml`) back to main. AC3 instead requires copying `acceptance/<id>/**` after verifier dispatch. E011 makes the same attempt-record-only boundary explicit to keep the governing main worktree separate from the subject branch. Change AC3 to keep acceptance files on the verifier branch and copy only `verification.yaml`. Test that a verifier's changed acceptance file leaves main byte-identical while remaining on the branch. This also requires a concrete way for main's `run-tests` to execute those branch tests without copying them into main; M01's candidate currently overlays acceptance files from the verifier commit when testing at base, so that path can be specified and checked.

2. **AC1 and AC10 do not define how dispatch uses M01's lifecycle.** AC1 requires the base recorded in `state.yaml`, yet AC10 dispatches from `READY` or `REWORK`, before M01's `start-build` has recorded the new attempt and base. M01's `start-build` also creates the worktree and changes state to `BUILDING`; `start-verify` similarly creates a worktree and changes state to `VERIFYING`. The M01 candidate's `cmd_dispatch` instead chooses its own base and branch. Specify whether dispatch calls those transitions or replaces their worktree creation, and require the resulting state to contain the exact retained branch, worktree and commit that `finish-build`/`finish-verify` will use. Test a successful dispatch followed by the relevant M01 finish command. AC1's promise that all-candidate failure leaves `state.yaml` unchanged also needs an explicit rollback or pre-transition path.

3. **AC2/AC3 can pass without a usable attempt record.** Both say “after a successful ... run” but do not require the agent to produce and commit `build.md` or `verification.yaml`. Dispatch could return zero and retain an empty or incomplete branch while the claimed artifact is absent; the M01 candidate currently prints a warning in that case. Require non-zero dispatch, no copy-back and no success metadata if the required record is missing or uncommitted. Cover both roles with an agent command that exits zero but writes no record.

4. **AC8's write boundary needs a Git exception and a fail-closed test.** A worktree commit must write Git's common metadata outside the worktree; the M01 candidate's Seatbelt profile permits the whole common `.git` directory and all of `/private/tmp`, while `run_agent_in_worktree` defaults to `use_seatbelt=False`. AC8 says only worktree and temporary directory are writable. State the narrow Git metadata writes needed for commits, require confinement on the dispatch path, and test a write to an unrelated path under `/private/tmp` as well as a write into main. Otherwise a permissive profile can satisfy the example while leaving the claimed boundary unenforced.

5. **Fallback cleanup is under-specified.** AC1 addresses cleanup only when every candidate exits non-zero; AC6 includes timeout, and neither criterion requires a failed candidate's worktree and branch to be removed *before* the next candidate starts. A failed candidate can leave files or commits that contaminate the next candidate's run, or a timeout can leave a child process writing after dispatch returns. Require a fresh worktree at the same recorded base for each candidate, cleanup of failed branches/worktrees and child processes after non-zero exit or timeout, and a test where the first candidate leaves a marker or child process and the second succeeds without seeing it.

These are specification changes, not implementation fixes. In particular, the M01 candidate is context for the lifecycle and sandbox risks; it is not integrated evidence that M02 already works.
