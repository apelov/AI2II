## Criteria that need correction

- **AC1, AC6, AC7, AC10:** These can all pass without proving the claimed wire exchange. AC1 requires UDP in both directions for the example, but neither PASS in DESIGN.md 24.20 nor AC6 requires a checker to validate those packets. AC7 only shows a checker can fail on one negative input; a checker could reject that file and accept every other file. AC10 only demands that the example vector checker reject a flipped byte. Add a required checker assertion for the actual exchange and a test where an unrelated nonempty pcap, or a pcap missing one direction, cannot produce PASS. Also require a positive vector matched to the observed wire bytes, not only a flipped-vector rejection.
- **AC2:** The phrase “after any single byte of any bundle file is changed” is broad, but the key missing negative case is an *extra* unlisted file. `SHA256SUMS` covering listed files can verify while an additional file is present, contradicting the stated “covering every other file” bundle contract. Require `verify-bundle` to reject unlisted files and a bundle with a missing or duplicate checksum entry. State whether it checks the bundle layout and verdict consistency or only integrity; otherwise “self-verifying evidence bundle” overclaims what this criterion proves.
- **AC3:** “A server that never answers” does not by itself force peer exit nonzero or checker failure under the specified verdict rule. The example must state the client's expected response behavior and a checker that detects its absence. Test a peer that hangs and spawns a child process, plus interruption, to establish the cleanup and timeout promise.
- **AC4, AC5:** The named negatives cover env failure, missing binary, and failed capture startup. Add an env check that fails after earlier checks passed, a peer build that exits nonzero while leaving an old declared binary, and a capture process that starts but records no packets. The old-binary case could otherwise yield a hollow PASS.
- **AC7, AC8:** The manifest errors are partly covered, but missing/empty `family`, duplicate peer/checker names, invalid `negative.replaces`, nonexistent negative input, and undefined peer names are unspecified. An absent family can bypass AC8. Define and test fail-closed validation before any build, peer start, or capture.
- **AC9:** “Rebuilding a changed peer source changes the recorded hash” is not a generally valid expectation: a source edit may leave binary bytes identical. Require the recorded hash to match the binary produced and used in this run, and test a build that actually changes binary bytes. Also test a missing binary and an existing stale binary after a failed build. Record the build result and binary path so the provenance is auditable.
- **AC11:** The two `grep` checks only detect literal imports or mentions; they can miss dynamic imports. More importantly, the criterion does not test that the governing `./orch` remains intact while a builder changes the subject `orchestrator.py`. Add an ownership/controller-boundary test tied to DESIGN.md 24.3, or leave that requirement to a prerequisite milestone with evidence.

The most consequential false-success path is: a permissive capture records unrelated UDP, a peer pair exits zero without a valid exchange, and a checker passes all normal inputs but fails its designated negative. The stated M08 acceptance can then look green while the bundle contains no evidence of the claimed interoperation. The spec should make this path fail before approval.
