# Design review 04

Scope: DESIGN.md 24.21, read with 24.20 and the COMPLETE M08 `wire/` implementation. I did not write the design. Local tool checks found Wireshark 4.6.9: `editcap --inject-secrets help` lists `tls`, and `tshark -U` lists `OSI layer 7` among its export taps. Python 3.14.6 exposes `SSLContext.keylog_filename`; with `SSLKEYLOGFILE` set, `ssl.create_default_context(ssl.Purpose.CLIENT_AUTH)` sets it, while a direct `SSLContext(PROTOCOL_TLS_SERVER)` does not. The TLS example must select a context factory that logs keys or set `keylog_filename` itself. These checks establish tool interfaces, not an end-to-end decrypted capture; no orchestrator run log for M09 exists.

## Findings

1. **Major — the wrong-secrets negative does not prove that the checker reads decrypted traffic.** A checker can inspect the substituted key file, pass when it contains the expected key text, and fail when it is altered, while ignoring `{decrypted}` entirely. The stated negative and `observes_decrypted` marker would then allow PASS without checking the decrypted view. M08's `wire/checkers.py` executes commands and compares exit codes; it cannot infer what a checker observed. Require a separate negative that replaces or corrupts the decrypted view while keeping the correct secrets, and require the checker to reject it. Reviewers must still assess whether the negative represents the claimed exchange. Falsify the current design early with a key-file-only checker against the TLS example.
2. **Major — the provenance claim is broader than the proposed evidence.** The self-challenge says the decrypt command and its inputs are hashed. M08 hashes the manifest and staged checker inputs, and requires a clean experiment directory, but it records only Python, git and tcpdump versions in `env.json` (`wire/run.py`). An external decrypt executable selected by the command, such as `editcap`, is neither pinned nor hashed by 24.21. The secret files will be covered by bundle SHA256SUMS, but that does not identify the tool that produced `capture-decrypted.pcapng`. Specify what identifies the decrypt executable and script, or narrow the provenance claim; test by changing the executable at a stable path without changing the manifest or secrets.
3. **Major — secret filenames need a boundary.** 24.21 calls them file names but does not explicitly require a relative path confined to `secrets/` or forbid symlinks that escape the bundle. The runner must use these names for output checks and negative substitution. Define and validate this boundary before any peer starts; a path such as `../capture.pcap` must fail manifest validation. This also protects the claim that `capture.pcap` is never modified.

The peer environment, optional command, two capture views, checker negatives and `contains_secrets` each serve the stated goal; I found no component without a goal or necessary abstraction beyond them. `wire/` can remain protocol-neutral: `asserts: encrypted` is a claim about a negative, while recognition stays in experiment checkers. Wireshark is an example dependency, not a generic runner dependency. The riskiest assumption is that negative-secret rejection demonstrates real decryption; finding 1 gives an immediate falsification experiment. The test-keys-only rule remains declared rather than enforced, as the design states, so bundle publication cannot be judged safe from `contains_secrets` alone.

Outcome: CHANGES_REQUESTED
