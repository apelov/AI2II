🎈 1. ELI5: Why AI Fails at Protocol Hackathons (And How AI2II Fixes It)

Imagine sitting at an IETF Hackathon table with draft-ietf-schc-8824-update-04. If you ask a single AI agent to "implement Section 5.2 and write tests", it will:

  • Misread subtle bit/byte framing or MUST NOT edge cases in the Internet-Draft,
  • Write unit tests that mirror its own misunderstanding (grading its own homework), and
  • Tell you "100% of tests pass!" — right until you try talking to another participant's implementation (./impl-python) and the packets fail on the wire.
Internet-Draft (draft-ietf-schc-8824-update-04) ──▶ Architect (Spec DAG) ──▶ [ Builder ⇄ Blind Verifier + Wire Mutants ] ──▶ Two-Peer Interop ──▶ Draft-Author Feedback
📜

1. Pin the Draft Clauses

The Architect extracts exact normative clauses (MUST, MUST NOT, packet formats) from Section 5.2 into falsifiable criteria (AC1, AC2, ...) locked by a SHA-256 hash.

🔨

2. Build in a Locked Worktree

The Builder implements the wire parser/state-machine in src/ inside an OS sandbox. It is physically blocked from editing acceptance tests or the spec.

🧬

3. Blind Verifier + Wire Mutants

A different AI model family reads the Internet-Draft directly (without seeing the Builder's notes), writes wire-level tests (valid, malformed, truncated), and proves each test fails when a protocol mutant is injected.

🤝

4. Two-Peer Interop & Feedback

./orch interop tests your ./impl-rust against ./impl-python (both Client→Server and reverse roles) and packages ambiguities for the draft authors.

🏆 What You Walk Away With at the End of the Hackathon (Deliverables A, B, C)

Deliverable A — Verified Protocol Code & Test Vectors

Working implementation + positive, negative, and malformed-byte conformance vectors in acceptance/M03/ proven against mutants.

Deliverable B — Reproducible Two-Peer Interop Matrix

Captured wire logs, exit codes, and interop_report.md between ./impl-rust and ./impl-python + a filled EXPERIMENT_RECORD.md.

Deliverable C — Structured Feedback to Draft Authors

Exact section references, ambiguities discovered (PROTOCOL_SPEC escalations & verifier could not verify items), and proposed clarifications for the IETF WG.

🧬 3. Protocol Mutant Cheat Sheet (How the Verifier Proves Tests Are Real)

In AI2II, a passing test is not accepted unless the Verifier proves the test fails when the protocol implementation is broken (fails_on: base or fails_on: mutant:<name>). Here are the 5 standard protocol mutants from docs/BEST_PRACTICES.md:

Mutant Name What the Patch Breaks in src/ What Protocol Bug It Proves Your Test Catches
mutant:wrong_constant Flips a magic byte, protocol version bit, or TLV type ID. Proves the test actually inspects wire header bytes instead of only checking return types.
mutant:truncate_buffer Slices payload[:-1] (reads N-1 bytes instead of N). Proves the parser test catches truncated packets and length-field mismatches.
mutant:skip_validation Comments out checksum, MIC, or header bounds validation. Proves negative tests (MUST reject in Section 5.2) actually trigger on corrupted frames.
mutant:invert_condition Changes boundary check if length > MAX_MTU to >= or <. Proves off-by-one boundary tests for RFC field limits are falsifiable.
mutant:ignore_exit_code Forces peer runner or decoder to return 0 on error. Proves interop harness tests detect peer crashes or silent rejection failures.
